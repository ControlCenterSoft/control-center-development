# Чтение событий аудита Control Center

## Назначение

Control Center хранит административные и security-события в append-only Audit-журнале. API чтения предназначен для уполномоченных администраторов и аудиторов, которым необходимо просматривать фактическую историю событий без изменения самого журнала.

Точка доступа:

`GET /api/v1/audit/events`

## Контроль доступа

Для чтения требуется одновременно:

- действующая аутентифицированная сессия;
- завершённая обязательная смена первоначального пароля после чистой установки;
- глобальное разрешение `audit.events.read`.

Отсутствие разрешения приводит к отказу. API не предоставляет обходного режима или неаутентифицированного экспорта.

## Ограниченное чтение

Ответ выдаётся страницами от новых событий к более старым. По умолчанию возвращается до 50 событий, максимальный размер страницы — 100.

Поддерживаются точные фильтры:

- `action` — действие;
- `outcome` — результат;
- `actor_id` — инициатор;
- `subject_id` — объект/субъект события;
- `event_id` — точный идентификатор одного Audit-события;
- `correlation_id` — точный идентификатор связанной операции/цепочки событий.

Фильтры объединяются по принципу AND. `event_id` не является полнотекстовым поиском: если указанный идентификатор не совпадает с сохранённым событием, результатом будет пустая ограниченная страница. `correlation_id` также сравнивается только целиком; похожие или частично совпадающие значения не считаются совпадением.

Несколько событий могут иметь один `correlation_id`, поэтому для корреляционной выборки сохраняются те же ограничения страницы и opaque cursor. Exact lookup не отключает pagination, RBAC, redaction или обязательную Audit-evidence запись самого чтения.

## Временное окно

Для ограниченной выборки по времени можно одновременно передать `from` и `to` в RFC 3339. Односторонняя граница не принимается: оба параметра обязательны вместе.

Граница `from` включается, а `to` исключается, то есть выбираются события с `occurred_at >= from` и `occurred_at < to`. Значения приводятся к UTC и точности PostgreSQL в микросекундах. `from` должен быть строго меньше `to`, а максимальная длительность одного запроса составляет 31 день. Интервал меньше точности хранилища и интервал, превышающий 31 день даже на одну наносекунду, отклоняются до чтения журнала.

Временное окно сочетается с точными фильтрами и pagination по принципу AND. Оно не превращает API в произвольный поиск или неограниченный экспорт.

Произвольный SQL, регулярные выражения, substring/prefix search, полнотекстовые условия и неограниченная выгрузка этим API не поддерживаются.

## Пагинация

Если доступны более старые события, ответ содержит `next_cursor`. Значение cursor является непрозрачным для клиента: его необходимо передать без изменения в следующем запросе как параметр `cursor`.

Клиент не должен строить cursor самостоятельно или полагаться на его внутренний формат. Некорректный, неизвестный или неоднозначный cursor отклоняется.

## Защита данных

Audit-журнал не предназначен для хранения значений паролей, session tokens, cookies, API keys, private keys или других credentials. Structured details проходят redaction при записи, а чтение повторно применяет безопасное представление данных.

Ответ помечается `Cache-Control: no-store`.

## Проверяемость чтения

Успешное чтение само формирует Audit-событие `audit.events_list` с результатом `success`. В evidence фиксируются параметры ограниченного запроса, включая exact `event_id`/`correlation_id`, нормализованные границы `from`/`to`, если они были заданы, и число возвращённых событий.

Если журнал можно прочитать, но evidence успешного чтения записать невозможно, Control Center возвращает ошибку и не отдаёт прочитанные события клиенту. Это сохраняет правило: привилегированное чтение Audit не должно происходить без собственной аудируемой записи.

Ошибка чтения журнала возвращается как временная недоступность и не преобразуется в пустую успешную страницу.

## Целостность

Чтение не изменяет существующие Audit-события и не ослабляет append-only свойства хранилища. Каждое загружаемое PostgreSQL-событие проверяется по сохранённому hash перед выдачей; ошибка декодирования или проверки приводит к fail-closed отказу запроса.

Полная проверка непрерывности всей hash-chain является отдельной операцией целостности и не заменяется обычным постраничным чтением.

## Пример последовательности

1. Запросить первую страницу с нужным точным фильтром и ограничением.
2. При необходимости ограничить выборку парой `from=<RFC3339>&to=<RFC3339>` длительностью не более 31 дня.
3. Для одного известного события использовать `event_id=<ID>`.
4. Для всех событий одной операции использовать `correlation_id=<ID>` и при необходимости проходить страницы через `next_cursor`.
5. Завершить чтение, когда `next_cursor` отсутствует.

Контракт API описан в `api/openapi-audit-events.yaml`.
