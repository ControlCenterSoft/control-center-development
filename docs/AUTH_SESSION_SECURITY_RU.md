# Control Center — безопасность пользовательских сессий

## Назначение

Control Center предоставляет локальной аутентифицированной учётной записи собственный контур управления активными сессиями. Пользователь может увидеть только свои действующие сессии, завершить одну выбранную сессию или немедленно завершить все свои активные сессии.

Контур предназначен для случаев потери устройства, подозрения на компрометацию браузерной сессии, проверки неизвестного входа или необходимости принудительно повторить аутентификацию на одном либо всех клиентах.

## API

### Просмотр собственных активных сессий

`GET /api/v1/auth/sessions`

Операция:

- требует действующую аутентифицированную сессию;
- недоступна до завершения обязательной смены первоначального пароля после чистой установки;
- возвращает только активные сессии текущей identity;
- помечает сессию, из которой выполнен запрос, полем `current=true`;
- может показывать время создания/истечения, source IP и ограниченный User-Agent для распознавания собственного устройства;
- никогда не возвращает session token, token digest, password hash или иной credential;
- не принимает идентификатор другого пользователя.

Список учитывает срок действия сессии, признак отзыва и текущую credential version. Сессия со старой credential version не считается действующей даже при наличии записи в storage.

### Завершение одной собственной сессии

`DELETE /api/v1/auth/sessions/{sessionID}`

Операция завершает только выбранную активную сессию, если она принадлежит текущей identity. Неизвестный, malformed, истёкший, уже отозванный или принадлежащий другому пользователю идентификатор возвращается единообразно как `404`, чтобы session-control API не превращался в механизм перечисления чужих сессий.

Если пользователь завершает текущую браузерную сессию, cookie удаляется и следующий защищённый запрос требует нового входа. Завершение другой собственной сессии не должно отзывать текущую.

### Завершение всех собственных сессий

`POST /api/v1/auth/sessions/revoke-all`

Операция:

- отзывает все активные сессии текущей учётной записи, включая сессию, из которой выполнен запрос;
- после успешного выполнения требует нового входа;
- не принимает идентификатор другого пользователя и поэтому не является административным API управления чужими сессиями;
- не возвращает и не записывает в Audit значения session token, cookie или пароля.

При cookie-аутентификации ответ также удаляет cookie текущей сессии. Успешный ответ имеет статус `204 No Content`.

## Audit и fail-closed граница

Просмотр собственных сессий фиксируется событием `auth.sessions_list` без credential material.

Перед отзывом одной сессии Control Center обязан успешно записать `auth.session_revoke` со статусом `requested`, actor/subject текущей identity и идентификатором собственной целевой сессии. Если обязательный Audit недоступен, mutation не начинается. После изменения записывается `success`; конкурентно исчезнувшая/уже изменённая цель фиксируется как `failed` без раскрытия токенов.

Перед отзывом всех сессий Control Center обязан успешно записать `auth.sessions_revoke_all` со статусом `requested`. Если обязательный Audit недоступен, отзыв сессий не начинается. После выполнения сохраняется `success` и количество отозванных сессий; при ошибке session store фиксируется `failed` без записи чувствительных значений.

Эти операции не изменяют пароль, RBAC-привязки, Desired State или инфраструктурные ресурсы.

## Проверяемые инварианты

- список не содержит чужих, истёкших, отозванных или credential-stale сессий;
- текущая сессия в списке определяется явно;
- завершение выбранной другой собственной сессии не влияет на текущую;
- завершение текущей сессии делает её немедленно недействительной и удаляет cookie;
- malformed и foreign session ID не позволяют определить существование чужой сессии;
- две и более активные сессии одного пользователя становятся недействительными после одного успешного `revoke-all`;
- повторное использование отозванного token приводит к отказу аутентификации;
- невозможность записать обязательное pre-mutation audit evidence блокирует mutation до изменения состояния;
- обязательный first-login password-change boundary остаётся приоритетным и не обходится через session-control API.

Формальный HTTP-контракт находится в `api/openapi-auth-session-controls.yaml`.
