# Актуальность проверки сетевых изменений

## Назначение

Контракт актуальности проверки дополняет безопасную поэтапную модель сетевых изменений Control Center. Он позволяет перед применением изменения однозначно проверить, что результаты обязательных проверок относятся к тому же плану и той же ревизии, не устарели и не были заменены неполными либо повреждёнными данными.

Контракт является только источником доказательств готовности. Он не выдаёт разрешение на изменение сети, не выполняет команды и не содержит учётные данные, адреса управляющих систем или произвольные исполняемые данные.

## Привязка доказательств

Доказательство содержит:

- версию схемы `network.change.verification-freshness/v1`;
- `plan_id` в форме `sha256:<digest>` точного канонического плана;
- `revision_id` точной ревизии;
- время формирования итоговой проверки;
- набор именованных проверок со статусом `PASS` или `FAIL`;
- SHA-256 digest доказательства каждой проверки;
- время наблюдения каждой проверки.

Проверка считается пригодной только для указанной пары `plan_id` + `revision_id`. Несовпадение любого из идентификаторов отклоняется fail-closed.

## Политика актуальности

Политика задаёт максимальный возраст доказательства, допустимое отклонение часов в будущее и закрытый список обязательных проверок.

Результат `ready=true` возможен только одновременно при всех условиях:

1. итоговое доказательство не старше допустимого возраста;
2. каждая обязательная проверка присутствует ровно один раз;
3. каждая обязательная проверка имеет статус `PASS`;
4. время каждой обязательной проверки находится в допустимом окне актуальности;
5. время проверки не выходит за границы итогового verification envelope;
6. все SHA-256 digest имеют корректный формат;
7. список обязательных проверок не содержит дубликатов.

Отсутствующая, устаревшая или завершившаяся `FAIL` проверка даёт `ready=false`. Повреждённые, неоднозначные или противоречивые входные данные отклоняются как ошибка контракта.

## Безопасность

Контракт сохраняет следующие инварианты:

- решение детерминировано для одинаковых входных данных и времени оценки;
- неизвестные статусы не трактуются как успех;
- дубликаты доказательств не используются для подмены результата;
- данные из будущего за пределами допустимого clock skew отклоняются;
- истёкшее доказательство нельзя переиспользовать для нового сетевого изменения;
- положительный результат не заменяет отдельные этапы авторизации, staged apply, connectivity probes и автоматического rollback;
- контракт не предоставляет production-mutation authority.

## Использование

Контракт предназначен для связывания preflight/verification evidence с точным сетевым change plan непосредственно перед переходом к разрешённому этапу применения. После изменения плана или ревизии прежнее доказательство должно считаться неприменимым и формироваться заново.
