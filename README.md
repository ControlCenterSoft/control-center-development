# Control Center

Control Center — самостоятельная платформа централизованного управления серверной и пользовательской ИТ-инфраструктурой с типизированной, проверяемой и аудируемой моделью выполнения операций.

**Последний опубликованный исходный релиз:** `0.6.0`.

**Последний выпуск отдельного стабильного бинарного канала:** `0.3.1`.

Эти каналы сейчас не синхронизированы по номеру версии: наличие опубликованного исходного релиза `0.6.0` не означает, что бинарный stable-канал уже содержит тот же состав.

## Назначение

Control Center предоставляет единый контур управления узлами, состоянием, изменениями, заданиями, инфраструктурными сервисами и устанавливаемыми модулями. Платформа строится вокруг разделения Desired State и Actual State: администратор задаёт требуемое состояние, система планирует изменение, проверяет ограничения и только после необходимых допусков может применять поддерживаемую операцию.

## Возможности опубликованного исходного релиза 0.6.0

- HTTP/JSON API, health и readiness;
- локальная модель identity/session;
- deny-by-default RBAC;
- append-oriented аудит;
- PostgreSQL-backed durable state;
- неизменяемые ревизии конфигурации;
- Changes с учётом политики, риска и требуемого approval;
- durable Jobs с leases, retries и idempotency;
- allowlisted typed actions вместо произвольного удалённого shell;
- состояние и health управляемых ресурсов;
- основы enrollment/heartbeat для узлов;
- основы Inventory, Market, PXE, Automation, Domain и Integration;
- Site-модель и безопасная автономная работа при временной потере WAN в пределах заранее делегированного scope;
- сетевые зоны WAN/LAN/MANAGEMENT/DMZ/CLUSTER/STORAGE/BACKUP;
- явное назначение Edge Gateway и запрет межзонной маршрутизации по умолчанию;
- staged network changes с проверками связности и rollback как контракт безопасности;
- нормализованная сетевая telemetry для Capacity Planner.

Сетевой слой `0.6.0` остаётся plan-only: наличие нескольких интерфейсов, включая WAN+LAN, не включает routing, forwarding, NAT или port-forwarding автоматически и не означает, что production network mutation уже доступна пользователю.

## Single-node и multi-node/HA

Control Center поддерживает самостоятельную single-node модель управления. Целевая архитектура также предусматривает распределение ролей между несколькими узлами, maintenance/drain, replacement/decommission, восстановление после потери узлов и HA-сценарии. Конкретная кластерная возможность считается доступной только тогда, когда она реализована, проверена и явно поддержана опубликованной версией и соответствующим каналом распространения.

## Capacity Planner

Capacity Planner — отдельная подсистема оценки безопасной ёмкости. Она должна учитывать CPU, RAM, storage, БД, сеть, workload profiles, telemetry, тренды роста и резерв на отказ. Опубликованный исходный `0.6.0` формирует часть исходных сетевых данных для такой оценки. Forecast, what-if, placement, bottleneck, horizon и последующие calibration-возможности относятся к кандидатным версиям после `0.6.0` и не должны описываться как функции стабильного бинарного выпуска `0.3.1`.

## Первый вход

В опубликованной исходной линии `0.6.0` целевая и реализованная локальная политика первого входа использует пользователя `admin` с первоначальным паролем `admin`, обязательной сменой этого пароля при первом входе и запретом обычной работы до смены. При обновлении существующий пользовательский пароль сохраняется и не должен заменяться первоначальным значением.

Отдельный стабильный бинарный выпуск `0.3.1` относится к более ранней модели bootstrap-аутентификации и не является подтверждением этой политики первого входа. Для установки необходимо применять правила аутентификации именно того бинарного релиза, который фактически используется.

## Безопасность изменений

Для опасной операции интерфейс и API должны явно показывать, что изменится, возможный риск, способ проверки результата и путь восстановления. Операции lifecycle узлов должны учитывать состояние ролей, данных и доступность сервисов. Network change считается применимой функцией только в тех версиях и профилях, где опубликована фактическая исполнительная реализация.

Core не предоставляет клиенту generic shell API. Исполнительная граница принимает только типизированные поддерживаемые действия с проверяемыми входами, полномочиями и audit correlation.

## Core и Market

**Core** содержит обязательные функции платформы: identity/RBAC, Desired/Actual State, Changes/Jobs, узлы и роли, сеть, состояние, monitoring/audit, recovery и базовые системные контракты.

**Market** содержит устанавливаемые инфраструктурные возможности. Модуль обязан иметь явную identity, compatibility/dependency metadata, требуемые permissions/capabilities и определённый lifecycle. Установка модуля не должна неявно расширять сетевые или привилегированные полномочия платформы.
