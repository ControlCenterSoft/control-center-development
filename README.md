# Control Center

Control Center — самостоятельная платформа централизованного управления серверной и пользовательской ИТ-инфраструктурой с типизированной, проверяемой и аудируемой моделью выполнения операций.

**Текущий опубликованный исходный релиз:** `0.6.0`.

## Назначение

Control Center предоставляет единый контур управления узлами, состоянием, изменениями, заданиями, инфраструктурными сервисами и устанавливаемыми модулями. Платформа строится вокруг разделения Desired State и Actual State: администратор задаёт требуемое состояние, система планирует изменение, проверяет ограничения и только после необходимых допусков может применять поддерживаемую операцию.

## Возможности текущего baseline 0.6.0

- HTTP/JSON API, health и readiness;
- локальная модель identity/session;
- deny-by-default RBAC;
- append-oriented аудит;
- PostgreSQL-backed durable state;
- неизменяемые ревизии конфигурации;
- Changes с учётом политики, риска и требуемого approval;
- durable Jobs с leases, retries и idempotency;
- allowlisted typed actions вместо произвольного удалённого shell;
- состояние и health управляемых ресурсов;
- основы enrollment/heartbeat для узлов;
- основы Inventory, Market, PXE, Automation, Domain и Integration;
- Site-модель и безопасная автономная работа при временной потере WAN в пределах заранее делегированного scope;
- сетевые зоны WAN/LAN/MANAGEMENT/DMZ/CLUSTER/STORAGE/BACKUP;
- явное назначение Edge Gateway и запрет межзонной маршрутизации по умолчанию;
- staged network changes с проверкой связности и автоматическим rollback;
- нормализованная сетевая telemetry для оценки ограничений и Capacity Planner.

Сетевые решения текущего релиза остаются plan-only: наличие нескольких интерфейсов, в том числе WAN+LAN, не включает routing, forwarding, NAT или port-forwarding автоматически. Такие функции могут применяться только как отдельные явно разрешённые операции.

## Single-node и multi-node/HA

Control Center поддерживает самостоятельную single-node модель управления. Целевая архитектура также предусматривает распределение ролей между несколькими узлами, maintenance/drain, replacement/decommission, восстановление после потери узлов и HA-сценарии. Конкретная кластерная возможность считается доступной пользователю только тогда, когда она реализована и явно поддержана установленной версией; наличие архитектурного контракта не следует трактовать как обещание уже доступного production failover.

## Capacity Planner

Capacity Planner является отдельной подсистемой оценки безопасной ёмкости. Он должен учитывать CPU, RAM, storage, БД, сеть, workload profiles, фактическую telemetry, тренды роста и резерв на отказ. В текущем `0.6.0` сетевой слой уже формирует нормализованные данные для такой оценки. Расширенные forecast/what-if возможности относятся к последующим версиям и не должны описываться как часть опубликованного `0.6.0`, пока соответствующий релиз не выпущен.

## Первый вход

После чистой установки создаётся локальный пользователь `admin` с первоначальным паролем `admin`. При первом входе пользователь обязан сменить пароль. До смены первоначального пароля обычная работа с системой запрещена.

При обновлении Control Center существующий пароль пользователя `admin` сохраняется: обновление не сбрасывает его и не возвращает значение `admin`.

## Безопасность изменений

Для опасной операции интерфейс и API должны явно показывать, что изменится, возможный риск, способ проверки результата и путь восстановления. Сетевые изменения выполняются по staged-модели с проверкой доступности и rollback. Операции lifecycle узлов должны учитывать состояние ролей, данных и доступность сервисов до вывода узла из эксплуатации.

Core не должен предоставлять клиенту generic shell API. Исполнительная граница принимает только типизированные поддерживаемые действия с проверяемыми входами, полномочиями и audit correlation.

## Core и Market

**Core** содержит обязательные функции платформы: identity/RBAC, Desired/Actual State, Changes/Jobs, узлы и роли, сеть, состояние, monitoring/audit, recovery и базовые системные контракты.

**Market** содержит устанавливаемые инфраструктурные возможности. Модуль обязан иметь явную identity, compatibility/dependency metadata, требуемые permissions/capabilities и определённый lifecycle. Установка модуля не должна неявно расширять сетевые или привилегированные полномочия платформы.
