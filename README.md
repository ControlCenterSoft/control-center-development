# Control Center

Control Center — самостоятельная платформа централизованного управления серверной и пользовательской ИТ-инфраструктурой с типизированной, проверяемой и аудируемой моделью выполнения операций.

**Последний опубликованный исходный релиз:** `0.9.0`.

Отдельный стабильный бинарный канал распространения пока подтверждён до `0.3.1`; это более ранняя бинарная линия и её эксплуатационные свойства нельзя автоматически приравнивать к возможностям исходного релиза `0.9.0`.

## Назначение

Control Center предоставляет единый контур управления узлами, состоянием, изменениями, заданиями, инфраструктурными сервисами и устанавливаемыми модулями. Платформа строится вокруг разделения Desired State и Actual State: администратор задаёт требуемое состояние, система планирует изменение, проверяет ограничения и только после необходимых допусков применяет поддерживаемую операцию.

## Опубликованная линия 0.6–0.9

`0.6.0` сформировал Site Autonomy и Network Foundation: иерархию Site, синхронизацию Desired/Actual State, делегированные offline-операции в ограниченном scope, сетевые зоны, явную роль Edge Gateway, staged network changes с проверкой связности/rollback и нормализованную network telemetry. Сетевые операции остаются безопасно ограниченными: наличие WAN+LAN не включает routing, forwarding, NAT или port-forwarding автоматически.

`0.7.0` добавил advisory Capacity Intelligence с детерминированными forecast и what-if моделями. `0.8.0` добавил детерминированный Placement Advice для выбора уже подходящего узла без назначения ролей или изменения Desired State. `0.9.0` добавил Bottleneck Report, который сопоставляет safe-capacity reserve и фактически ограничивающую метрику и выдаёт только рекомендательное действие.

Capacity-функции 0.7–0.9 являются **advisory-only**: они не выполняют placement, migration, resize, закупку ресурсов или другие инфраструктурные изменения автоматически.

## Single-node и multi-node/HA

Control Center поддерживает самостоятельную single-node модель управления. Целевая архитектура также предусматривает распределение ролей, maintenance/drain, replacement/decommission, восстановление после потери узлов и HA-сценарии. Возможность считается реально поддержанной только для тех ролей и версий, где опубликован и проверен соответствующий failure/recovery профиль; наличие архитектурного контракта само по себе не доказывает production failover.

## Desired/Actual State и безопасность изменений

Опасные операции выполняются через контролируемые Change/Job границы, с проверкой permissions, актуальности состояния, риска, результата и пути recovery/rollback. Core не предоставляет пользователю generic shell API; исполнительная граница принимает только типизированные поддерживаемые действия.

Для сетевых изменений действует staged-модель: предварительная проверка, временное применение, connectivity verification и автоматический rollback при потере управляемости. NAT/port-forwarding включаются только явно.

## Core и Market

**Core** включает identity/RBAC, Desired/Actual State, Changes/Jobs, узлы и роли, lifecycle, сеть, monitoring/health, audit, recovery-контракты, Capacity Planner foundation и системные API.

**Market** содержит устанавливаемые инфраструктурные возможности. Для модуля должны быть определены identity, compatibility/dependencies, permissions/capabilities, network/storage requirements, capacity profile, backup/recovery и lifecycle. К направлениям Market относятся Directory Services с поддерживаемыми providers (включая Samba AD и FreeIPA там, где применимо), DNS/DHCP, PXE для Windows/Linux, Software Automation для Windows/Linux, Inventory/Compliance, File Services, Monitoring, Backup и другие совместимые инфраструктурные providers.

## Первый вход

Для опубликованной исходной линии начиная с `0.6.0` чистая установка создаёт локального пользователя `admin` с первоначальным паролем `admin`. При первом входе пользователь обязан сменить пароль; до смены обычная работа запрещена. При обновлении существующий пароль администратора сохраняется и не заменяется первоначальным значением.

Отдельный stable-binary выпуск `0.3.1` относится к более ранней bootstrap-модели аутентификации, поэтому его поведение следует проверять по документации именно этой версии.
